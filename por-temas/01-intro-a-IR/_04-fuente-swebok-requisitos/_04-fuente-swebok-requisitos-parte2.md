## 3. Elicitación de requisitos

`[1*, c4s5] [2*, c5, c6, c9]`

La elicitación de requisitos se ocupa de los orígenes de los requisitos de software y de cómo el ingeniero de software puede recolectarlos. Es la primera etapa en la construcción de un entendimiento del problema que el software debe resolver. Es fundamentalmente una actividad humana, y es donde se identifica a los stakeholders y se establecen las relaciones entre el equipo de desarrollo y el cliente. Se la denomina de diversas maneras: "captura de requisitos", "descubrimiento de requisitos" y "adquisición de requisitos".

Uno de los principios fundamentales de un buen proceso de elicitación de requisitos es el de la comunicación efectiva entre los diversos stakeholders. Esta comunicación continúa a lo largo de todo el proceso del ciclo de vida de desarrollo de software (SDLC), con distintos stakeholders en distintos momentos. Antes de que comience el desarrollo, los especialistas en requisitos pueden constituir el canal de esa comunicación. Deben mediar entre el dominio de los usuarios del software (y otros stakeholders) y el mundo técnico del ingeniero de software. Un conjunto de modelos internamente consistentes, a distintos niveles de abstracción, facilita las comunicaciones entre los usuarios/stakeholders del software y los ingenieros de software.

Un elemento crítico de la elicitación de requisitos es informar el alcance del proyecto. Esto implica proporcionar una descripción del software que se está especificando y de su propósito, y priorizar los entregables para asegurar que las necesidades de negocio más importantes del cliente se satisfagan primero. Esto minimiza el riesgo de que los especialistas en requisitos gasten tiempo elicitando requisitos de baja importancia, o requisitos que terminan resultando irrelevantes para cuando el software se entrega. Por otro lado, la descripción debe ser escalable y extensible, de modo de aceptar requisitos adicionales no expresados en las primeras listas formales y compatibles con los anteriores, tal como lo contemplan los métodos recursivos.

### 3.1. Fuentes de requisitos

Los requisitos tienen muchas fuentes en el software típico, y es esencial que todas las fuentes potenciales sean identificadas y evaluadas. Este tópico está diseñado para promover la conciencia de las diversas fuentes de requisitos de software y de los marcos para gestionarlas. Los puntos principales que se cubren son los siguientes:

- **Objetivos.** El término "objetivo" (a veces llamado "preocupación de negocio" o "factor crítico de éxito") se refiere a las metas generales y de alto nivel del software. Los objetivos proporcionan la motivación para el software, pero a menudo están formulados de manera vaga. Los ingenieros de software necesitan prestar particular atención a evaluar el valor (en relación con la prioridad) y el costo de los objetivos. Un estudio de factibilidad es una manera relativamente económica de hacerlo.
- **Conocimiento del dominio.** El ingeniero de software necesita adquirir, o tener disponible, conocimiento sobre el dominio de aplicación. El conocimiento del dominio proporciona el trasfondo contra el cual debe situarse todo el conocimiento de requisitos elicitado, para poder entenderlo. Es una buena práctica emular un enfoque ontológico en el dominio de conocimiento. Deberían identificarse las relaciones entre los conceptos relevantes dentro del dominio de aplicación.
- **Stakeholders** (ver sección 2.2, Actores del proceso). Mucho software ha resultado insatisfactorio porque enfatizó los requisitos de un grupo de stakeholders a expensas de otros. En consecuencia, el software entregado resulta difícil de usar, o subvierte las estructuras culturales o políticas de la organización cliente. El ingeniero de software necesita identificar, representar y gestionar los "puntos de vista" de muchos tipos distintos de stakeholders.
- **Reglas de negocio.** Son enunciados que definen o restringen algún aspecto de la estructura o del comportamiento del negocio en sí. "Un estudiante no puede inscribirse en las materias del cuatrimestre siguiente si quedan aranceles impagos" sería un ejemplo de una regla de negocio que constituiría una fuente de requisitos para el software de inscripción a materias de una universidad.
- **El entorno operacional.** Se derivarán requisitos del entorno en el cual se ejecutará el software. Pueden ser, por ejemplo, restricciones de temporización en software de tiempo real, o restricciones de rendimiento en un entorno de negocio. Deben buscarse activamente, porque pueden afectar enormemente la factibilidad y el costo del software, además de restringir las opciones de diseño.
- **El entorno organizacional.** A menudo se requiere que el software dé soporte a un proceso de negocio, cuya selección puede estar condicionada por la estructura, la cultura y la política interna de la organización. El ingeniero de software necesita ser sensible a estos factores ya que, en general, el software nuevo no debería forzar cambios no planificados sobre el proceso de negocio.

### 3.2. Técnicas de elicitación

Una vez identificadas las fuentes de requisitos, el ingeniero de software puede comenzar a elicitar información de requisitos a partir de ellas. Nótese que rara vez los requisitos se elicitan ya hechos. Más bien, el ingeniero de software elicita información a partir de la cual formula los requisitos. Este tópico se concentra en técnicas para lograr que los stakeholders humanos articulen información relevante para los requisitos. Es una tarea muy difícil, y el ingeniero de software necesita estar sensibilizado al hecho de que (por ejemplo) los usuarios pueden tener dificultad para describir sus tareas, pueden dejar información importante sin enunciar, o pueden no estar dispuestos o no ser capaces de cooperar. Es particularmente importante entender que la elicitación no es una actividad pasiva y que, incluso si hay stakeholders cooperativos y articulados disponibles, el ingeniero de software tiene que trabajar duro para elicitar la información correcta. Muchos requisitos de negocio o técnicos son tácitos, o están en retroalimentación que todavía no se obtuvo de los usuarios finales. La importancia de la planificación, la verificación y la validación en la elicitación de requisitos no puede exagerarse. Existen varias técnicas para la elicitación de requisitos; las principales son estas:

- **Entrevistas.** Entrevistar a los stakeholders es un medio "tradicional" de elicitar requisitos. Es importante entender las ventajas y limitaciones de las entrevistas y cómo deberían conducirse.
- **Escenarios.** Los escenarios proporcionan un medio valioso para aportar contexto a la elicitación de requisitos de usuario. Le permiten al ingeniero de software proveer un marco para las preguntas sobre las tareas del usuario, al habilitar que se formulen preguntas del tipo "¿qué pasa si...?" y "¿cómo se hace esto?". El tipo de escenario más común es la descripción de caso de uso. Hay aquí un vínculo con el tópico 4.2 (Modelado conceptual), porque las notaciones de escenarios, como los diagramas de casos de uso, son habituales en el modelado de software.
- **Prototipos.** Esta técnica es una herramienta valiosa para clarificar requisitos ambiguos. Pueden actuar de manera similar a los escenarios, dándoles a los usuarios un contexto dentro del cual pueden entender mejor qué información necesitan proporcionar. Existe un amplio rango de técnicas de prototipado —desde maquetas en papel de diseños de pantalla hasta versiones beta de productos de software— y una fuerte superposición entre sus usos separados para la elicitación de requisitos y para la validación de requisitos (ver sección 6.2, Prototipado). A menudo se prefieren los prototipos de baja fidelidad, para evitar que el stakeholder se "ancle" en características menores e incidentales de un prototipo de mayor calidad, lo que puede limitar la flexibilidad de diseño de maneras no buscadas.
- **Reuniones facilitadas.** El propósito de estas reuniones es intentar lograr un efecto sumativo, por el cual un grupo de personas puede aportar más comprensión sobre sus requisitos de software que trabajando individualmente. Pueden hacer *brainstorming* y refinar ideas que sería difícil traer a la superficie mediante entrevistas. Otra ventaja es que los requisitos en conflicto emergen tempranamente, de una manera que les permite a los stakeholders reconocer dónde ocurren. Cuando funciona bien, esta técnica puede dar como resultado un conjunto de requisitos más rico y más consistente del que sería alcanzable de otro modo. Sin embargo, las reuniones deben manejarse con cuidado (de ahí la necesidad de un facilitador) para prevenir una situación en la que las capacidades críticas del equipo se vean erosionadas por la lealtad al grupo, o en la que requisitos que reflejan las preocupaciones de unas pocas personas de voz fuerte (y quizá de mayor jerarquía) que son favorecidos en detrimento de las demás.
- **Observación.** La importancia del contexto del software dentro del entorno organizacional ha llevado a la adaptación de técnicas observacionales, como la etnografía, para la elicitación de requisitos. Los ingenieros de software aprenden sobre las tareas de los usuarios sumergiéndose en el entorno y observando cómo los usuarios realizan sus tareas al interactuar entre sí, con las herramientas de software y con otros recursos. Estas técnicas son relativamente costosas, pero también instructivas, porque ilustran que muchas tareas de usuario y procesos de negocio son demasiado sutiles y complejos como para que sus actores los describan con facilidad.
- **Historias de usuario.** Esta técnica se usa comúnmente en métodos adaptativos (ver Métodos ágiles en la KA de Modelos y Métodos de Ingeniería de Software) y se refiere a descripciones breves y de alto nivel de la funcionalidad requerida, expresadas en los términos del cliente. Una historia de usuario típica tiene la forma: "Como \<rol\>, quiero \<objetivo/deseo\> para \<beneficio\>". Se busca que una historia de usuario contenga apenas la información suficiente como para que los desarrolladores puedan producir una estimación razonable del esfuerzo de implementarla. El objetivo es evitar parte del desperdicio que suele ocurrir en proyectos donde los requisitos detallados se recolectan tempranamente pero quedan inválidos antes de que el trabajo comience. Antes de que una historia de usuario se implemente, el cliente debe escribir un procedimiento de aceptación apropiado para determinar si los objetivos de la historia de usuario se cumplieron.
- **Otras técnicas.** Existe un abanico de otras técnicas para dar soporte a la elicitación de información de requisitos, que va desde analizar los productos de los competidores hasta aplicar técnicas de minería de datos, pasando por usar fuentes de conocimiento del dominio o bases de datos de pedidos de clientes.

## 4. Análisis de requisitos

`[1*, c4s1, c4s5, c10s4, c12s5] [2*, c7, c11, c12, c17]`

Este tópico se ocupa del proceso de analizar los requisitos para

- detectar y resolver conflictos entre requisitos;
- descubrir los límites del software y cómo debe interactuar con su entorno organizacional y operacional;
- elaborar los requisitos de sistema para derivar los requisitos de software.

La visión tradicional del análisis de requisitos ha sido que se reduzca al modelado conceptual, usando alguno de varios métodos de análisis, como el método de análisis estructurado. Si bien el modelado conceptual es importante, incluimos la clasificación de requisitos para ayudar a fundamentar los *tradeoffs* entre requisitos (clasificación de requisitos) y el proceso de establecer esos *tradeoffs* (negociación de requisitos).

Debe cuidarse de describir los requisitos con la precisión suficiente como para permitir que los requisitos sean validados, que su implementación sea verificada y que sus costos sean estimados.

### 4.1. Clasificación de requisitos

Los requisitos pueden clasificarse según varias dimensiones. Algunos ejemplos son los siguientes:

- Si el requisito es funcional o no funcional (ver sección 1.3, Requisitos funcionales y no funcionales).
- Si el requisito se deriva de uno o más requisitos de alto nivel o de una propiedad emergente (ver sección 1.4, Propiedades emergentes), o si está siendo impuesto directamente sobre el software por un stakeholder o alguna otra fuente.
- Si el requisito es sobre el producto o sobre el proceso (ver sección 1.2, Requisitos de producto y requisitos de proceso). Los requisitos sobre el proceso pueden restringir la elección del contratista, el proceso de ingeniería de software que se adoptará, o los estándares a los que hay que adherir.
- La prioridad del requisito. Cuanto mayor es la prioridad, más esencial resulta el requisito para cumplir con los objetivos generales del software. A menudo clasificada en una escala de puntos fijos, como obligatorio, altamente deseable, deseable u opcional, la prioridad suele tener que balancearse contra el costo de desarrollo e implementación.
- El alcance del requisito. El alcance se refiere a la medida en que un requisito afecta al software y a sus componentes. Algunos requisitos, en particular ciertos requisitos no funcionales, tienen un alcance global, en el sentido de que su satisfacción no puede asignarse a un componente discreto. En consecuencia, un requisito con alcance global puede afectar fuertemente a la arquitectura del software y al diseño de muchos componentes, mientras que uno con alcance acotado puede ofrecer varias opciones de diseño y tener poco impacto sobre la satisfacción de otros requisitos.
- Volatilidad/estabilidad. Algunos requisitos cambiarán durante el ciclo de vida del software, e incluso durante el propio proceso de desarrollo. Es útil poder hacer alguna estimación de la probabilidad de que un requisito cambie. Por ejemplo, en una aplicación bancaria, los requisitos de las funciones para calcular y acreditar intereses en las cuentas de los clientes probablemente sean más estables que un requisito de dar soporte a un tipo particular de cuenta libre de impuestos. El primero refleja una característica fundamental del dominio bancario (que las cuentas pueden generar intereses), mientras que el segundo puede volverse obsoleto por un cambio en la legislación gubernamental. Señalar los requisitos potencialmente volátiles puede ayudar al ingeniero de software a establecer un diseño más tolerante al cambio.

Pueden resultar apropiadas otras clasificaciones, dependiendo de la práctica habitual de la organización y de la propia aplicación.

Hay una fuerte superposición entre la clasificación de requisitos y los atributos de requisitos (ver sección 7.3, Atributos de requisitos).

### 4.2. Modelado conceptual

El desarrollo de modelos de un problema del mundo real es clave para el análisis de requisitos de software. Su propósito es ayudar a comprender la situación en la que ocurre el problema, así como a representar una solución. En consecuencia, los modelos conceptuales comprenden modelos de entidades del dominio del problema, configurados para reflejar sus relaciones y dependencias del mundo real. Este tópico se relaciona estrechamente con la KA de Modelos y Métodos de Ingeniería de Software.

Pueden desarrollarse varios tipos de modelos. Entre ellos, diagramas de casos de uso, modelos de flujo de datos, modelos de estados, modelos basados en objetivos, interacciones de usuario, modelos de objetos, modelos de datos y muchos otros. Muchas de estas notaciones de modelado son parte del Lenguaje Unificado de Modelado (UML). Los diagramas de casos de uso, por ejemplo, se usan rutinariamente para representar escenarios en los que la frontera separa a los actores (usuarios o sistemas del entorno externo) del comportamiento interno, donde cada caso de uso representa una funcionalidad del sistema.

Los factores que influyen en la elección de la notación de modelado incluyen estos:

- **La naturaleza del problema.** Algunos tipos de software exigen que ciertos aspectos se analicen con particular rigor. Por ejemplo, los modelos de estados y los modelos paramétricos, que son parte de SysML [4], probablemente sean más importantes para software de tiempo real que para sistemas de información, mientras que usualmente ocurriría lo opuesto con los modelos de objetos y de actividades.
- **La experiencia del ingeniero de software.** A menudo es más productivo adoptar una notación o método de modelado con el que el ingeniero de software tenga experiencia.
- **Los requisitos de proceso del cliente** (ver sección 1.2, Requisitos de producto y requisitos de proceso). Los clientes pueden imponer su notación o método preferido, o prohibir cualquiera con el que no estén familiarizados. Este factor puede entrar en conflicto con el factor anterior.

Nótese que, en casi todos los casos, es útil comenzar construyendo un modelo del contexto del software. El contexto del software proporciona una conexión entre el software previsto y su entorno externo. Esto es crucial para comprender el contexto del software en su entorno operacional y para identificar sus interfaces con el entorno.

Este subtópico no busca "enseñar" un estilo o notación de modelado en particular, sino que proporciona orientación sobre el propósito y la intención del modelado.

### 4.3. Diseño arquitectónico y asignación de requisitos

En algún punto, la arquitectura de la solución debe derivarse. El diseño arquitectónico es el punto en el que el proceso de requisitos se superpone con el diseño de software o de sistemas, e ilustra lo imposible que resulta desacoplar limpiamente las dos tareas. Este tópico se relaciona estrechamente con Estructura y arquitectura del software, en la KA de Diseño de Software. En muchos casos, el ingeniero de software actúa como arquitecto de software, porque el proceso de analizar y elaborar los requisitos exige que se identifiquen los componentes de arquitectura/diseño que serán responsables de satisfacer los requisitos. Esto es la asignación de requisitos: la adjudicación a los componentes de arquitectura responsables de satisfacer los requisitos.

La asignación es importante para permitir un análisis detallado de los requisitos. Así, por ejemplo, una vez que un conjunto de requisitos ha sido asignado a un componente, los requisitos individuales pueden analizarse aún más para descubrir requisitos adicionales sobre cómo el componente necesita interactuar con otros componentes para satisfacer los requisitos asignados. En proyectos grandes, la asignación estimula una nueva ronda de análisis para cada subsistema. Como ejemplo, los requisitos de un determinado rendimiento de frenado para un auto (distancia de frenado, seguridad en malas condiciones de manejo, suavidad de aplicación, presión de pedal requerida, etcétera) pueden asignarse al hardware de frenado (conjuntos mecánicos e hidráulicos) y a un sistema de frenos antibloqueo (ABS). Recién cuando un requisito para un sistema de frenos antibloqueo ha sido identificado, y los requisitos le han sido asignados, pueden usarse las capacidades del ABS, el hardware de frenado y las propiedades emergentes (como el peso del auto) para identificar los requisitos de software detallados del ABS.

El diseño arquitectónico se identifica estrechamente con el modelado conceptual (ver sección 4.2, Modelado conceptual).

### 4.4. Negociación de requisitos

Otro término usado comúnmente para este subtópico es "resolución de conflictos". Se refiere a resolver problemas con los requisitos allí donde ocurren conflictos: entre dos stakeholders que requieren *features* mutuamente incompatibles, entre requisitos y recursos, o entre requisitos funcionales y no funcionales, por ejemplo. En la mayoría de los casos, no es prudente que el ingeniero de software tome una decisión unilateral, de modo que se vuelve necesario consultar con el o los stakeholders para alcanzar un consenso sobre un *tradeoff* apropiado. A menudo es importante, por razones contractuales, que tales decisiones sean trazables hacia atrás hasta el cliente. Hemos clasificado esto como un tópico de análisis de requisitos de software porque los problemas emergen como resultado del análisis. Sin embargo, también puede argumentarse con fuerza a favor de considerarlo un tópico de validación de requisitos (ver tópico 6, Validación de requisitos).

La priorización de requisitos es necesaria no solo como medio para filtrar los requisitos importantes, sino también para resolver conflictos y planificar entregas escalonadas, lo que implica tomar decisiones complejas que requieren conocimiento detallado del dominio y buenas habilidades de estimación. Sin embargo, a menudo es difícil obtener información real que pueda servir de base para tales decisiones. Además, los requisitos frecuentemente dependen unos de otros, y las prioridades son relativas. En la práctica, los ingenieros de software realizan priorización de requisitos con frecuencia sin conocer todos los requisitos. La priorización de requisitos puede seguir un enfoque costo-valor, que involucra un análisis por parte de los stakeholders que definen en una escala los beneficios o el valor agregado que la implementación del requisito les aporta, frente a las penalidades de no haber implementado un requisito en particular. También involucra un análisis por parte de los ingenieros de software, que estiman en una escala el costo de implementar cada requisito en relación con los otros requisitos. Otro enfoque de priorización de requisitos, llamado proceso de análisis jerárquico, consiste en comparar todos los pares únicos de requisitos para determinar cuál de los dos es de mayor prioridad, y en qué medida.

### 4.5. Análisis formal

El análisis formal concierne no solo al tópico 4, sino también a las secciones 5.3 y 6.3. Este tópico se relaciona además con Métodos formales, en el Área de Conocimiento de Modelos y Métodos de Ingeniería de Software.

El análisis formal ha tenido impacto en algunos dominios de aplicación, particularmente en los de sistemas de alta integridad. La expresión formal de requisitos requiere un lenguaje con semántica formalmente definida. El uso de un análisis formal para la expresión de requisitos tiene dos beneficios. Primero, permite que los requisitos expresados en el lenguaje se especifiquen de manera precisa y no ambigua, evitando así (en principio) el potencial de mala interpretación. Segundo, es posible razonar sobre los requisitos, lo que permite demostrar propiedades deseadas del software especificado. El razonamiento formal requiere soporte de herramientas para ser practicable en cualquier caso que no sea trivial, y las herramientas generalmente caen en dos tipos: demostradores de teoremas o verificadores de modelos. En ninguno de los dos casos puede la demostración automatizarse por completo, y el nivel de competencia en razonamiento formal necesario para usar las herramientas restringe la aplicación más amplia del análisis formal.

La mayor parte del análisis formal se enfoca en etapas relativamente tardías del análisis de requisitos. Generalmente es contraproducente aplicar la formalización hasta que los objetivos de negocio y los requisitos de usuario hayan alcanzado un foco nítido, mediante medios como los descritos en otras partes de la sección 4. Sin embargo, una vez que los requisitos se han estabilizado y han sido elaborados para especificar propiedades concretas del software, puede resultar beneficioso formalizar al menos los requisitos críticos. Esto permite la validación estática de que el software especificado por los requisitos efectivamente tiene las propiedades (por ejemplo, ausencia de *deadlock*) que el cliente, los usuarios y el ingeniero de software esperan que tenga.
